<diagnosis>
Empirically established against the running compose stack — do NOT re-derive.

**There are TWO failure modes, thrown from two different layers.** The `04-SECURITY.md` T-04 entry
attributes both to the Postgres `22008` cast error; that attribution is incomplete.

| Input | `new Date(day + "T00:00:00.000Z")` | Where the 500 originates |
|---|---|---|
| `2026-02-30` | **valid** — JS silently rolls over to Mar 2 | reaches SQL; Postgres rejects `'2026-02-30'::date` → error `22008`, at `route.ts:59` |
| `2026-99-99`, `2026-13-01`, `2026-00-10`, `2026-01-32` | **Invalid Date** | `.toISOString()` throws `RangeError: Invalid time value` at **`route.ts:57`** — SQL never runs |

**Consequence that governs this plan:** a `try`/`catch` wrapped around only the `db.$queryRaw` /
`Promise.all` block would NOT catch the second class. Line 57 executes before line 59. Such a fix
looks complete and still returns 500 for `2026-99-99`.

**A silent correctness bug rides along.** Because JS rolls `2026-02-30` forward to Mar 2,
`yesterdayStr` becomes `2026-03-01` while `day` stays `2026-02-30` — two values derived from one
input that disagree. Postgres currently masks this by rejecting the cast.

**Live HTTP status today:** `?day=2026-02-30` → 500 · `?day=2026-99-99` → 500 · `?day=2026-01-05` → 200.
Response body on the 500s is **empty** — no stack trace or schema internals reach the client. This is a
robustness / first-impression defect, **not** an information-disclosure one. Do not overstate it.

**Scope is genuinely one route.** Every sibling was probed and returns 200:
`/api/losses?day=2026-99-99` → 200 (shares the permissive regex but string-compares `shiftDate` with
no `::date` cast, so nonsense dates yield empty rows) · `/api/timeline?shiftDate=2026-99-99` → 200 ·
`/api/timeline?shiftDate=notadate` → 200 · `/api/oee?shiftDate=2026-99-99` → 200 · `/api/dds` derives
its dates from `sim_now()` server-side with no user-controlled date at all. Fix `/api/orders` only.
</diagnosis>

<decisions>

## D-01 — Hand-rolled round-trip check, NOT zod

A single round-trip predicate — parse the string, then assert the parsed Date re-serializes to the
original string — kills **both** failure classes with one check: `2026-99-99` fails the NaN guard,
`2026-02-30` re-serializes as `2026-03-02` and fails the equality.

**Chosen: hand-rolled.** Three reasons, in order of weight:

1. **zod is not a dependency of `apps/web`.** Verified: `apps/web/package.json` deps are
   `@linelens/db`, `echarts`, `next`, `pg`, `react`, `react-dom`. zod `4.4.3` exists only in
   `apps/simulator` and `packages/contracts`, neither of which `apps/web` depends on — and pnpm's
   strict `node_modules` means there is no phantom resolution. Adding it costs a manifest edit, a
   lockfile change, and a Docker image rebuild, to validate one scalar query param.
2. **CLAUDE.md scopes zod's mandate narrowly.** The stack table's zod row reads: *"Validate MQTT JSON
   payloads (PackTags-lite) + env/config"* — structured, untrusted-shape objects crossing a process
   boundary. A `YYYY-MM-DD` scalar is not that boundary. The parse-don't-validate *spirit* is honored
   regardless, because the helper returns the **parsed derived value** (`yesterday`) rather than a
   bare boolean — the caller cannot re-derive it wrongly.
3. **The precedent argument cuts against zod here.** Introducing zod to the web tier to fix one route
   invites it into `/api/losses`, `/api/timeline`, and `/api/oee`, none of which currently need it.
   A pure module under `src/lib/` is the *smaller*, already-established precedent.

Honest counterweight: zod 4's `z.iso.date()` does perform real calendar validation, so the
alternative is genuinely defensible — it is rejected on dependency cost and mandate scope, not on
capability.

## D-02 — Extract the predicate to a pure module; do not attempt a route-handler unit test

A true unit test of the route handler is **impractical in this repo today**, verified rather than
assumed:

- `apps/web` has **no** `vitest.config.*` and no vite config of any kind. It is picked up purely by
  the root `vitest.config.ts` `projects: ["packages/*", "apps/*"]` glob via its `package.json`.
- The `@/*` → `./src/*` alias exists **only** in `apps/web/tsconfig.json` `paths`. TypeScript honors
  it; Vite/Vitest does not, absent a `resolve.alias` or `vite-tsconfig-paths`. So a test importing
  `../src/app/api/orders/route` fails to resolve its `import { db } from "@/lib/db"`.
- Even with an alias added, module evaluation calls `createDb()` from `@linelens/db/client` at import
  time, which would need a Prisma-singleton mock.
- All 7 existing `apps/web/test/*.test.ts` files import pure modules by **relative** path
  (`../src/lib/loss-pareto`, `../src/lib/order-headline`, `../src/lib/timeline-data`,
  `../src/lib/oee-waterfall`, `../src/hooks/use-live`). There are zero route-handler tests.

**Most valuable testable seam: the pure predicate.** `apps/web/src/lib/order-headline.ts` states the
precedent in its own header — *"pure-core / component-shell split … so the exact copy is unit-testable
without rendering React."* `day-param.ts` follows it exactly. Standing up vitest alias config plus
Prisma mocking infrastructure to cover a two-line guard is not worth it; the route-level behavior is
covered by the live `curl` gate in Task 2 instead.

## D-03 — 400 body shape matches the route's existing contract

The new rejection path reuses the route's existing shape from line 52 — `{ error: "…" }` at status
400 — so clients see one consistent error contract regardless of which validation rule tripped.

    Create `apps/web/src/lib/day-param.ts` exporting a single pure function `parseDayParam(day: string | null): { day: string; yesterday: string } | null`, plus its return interface. No imports from `@/lib/db`, no Prisma, no I/O — the module must stay DB-free so it is testable by relative import under the existing vitest setup (see D-02).

    Algorithm, in this exact order — the ordering is load-bearing:

    1. Null/shape guard: return `null` unless `day` is a non-empty string matching `/^\d{4}-\d{2}-\d{2}$/`. Keep this regex identical to the one being replaced in `route.ts:51` so the shape contract does not change.
    2. Parse: build a `Date` from the template `${day}T00:00:00.000Z`.
    3. **NaN guard, BEFORE any `toISOString()` call:** if `Number.isNaN(parsed.getTime())`, return `null`. This ordering is the entire fix for the Invalid-Date class — calling `toISOString()` on an Invalid Date is what throws `RangeError` at `route.ts:57` today. Do not reorder these two steps.
    4. **Round-trip guard:** if `parsed.toISOString().slice(0, 10)` does not strictly equal `day`, return `null`. This rejects the silent-rollover class (`2026-02-30` re-serializes as `2026-03-02`).
    5. Derive `yesterday` from the SAME validated `parsed` value — construct a fresh `Date` from `parsed.getTime()`, apply `setUTCDate(getUTCDate() - 1)`, and `slice(0, 10)` its `toISOString()`. Deriving from the already-validated instant is what makes `day` and `yesterday` structurally unable to disagree.
    6. Return both.

    Write a module header docblock in the house style: name the two failure classes it closes, cite T-04 and `04-SECURITY.md`, and record that step 3 must precede step 4. Note that the round-trip check produces no false rejections inside the regex's 4-digit-year domain — `toISOString()` zero-pads years below 1000, so `0999-01-01` round-trips cleanly.

    Run the test to confirm RED before writing the implementation, then GREEN after.
  </action>
