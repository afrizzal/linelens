# Feature Research

**Domain:** Real-time OEE / manufacturing analytics dashboard (portfolio-first, simulated build)
**Researched:** 2026-07-22
**Confidence:** HIGH for table-stakes / OEE mechanics (from adversarially-verified `docs/00-domain-research.md`), MEDIUM for gap-fill items (shift-calendar UX, reason-code entry UX, report export, demo-mode) and DIFOT differentiator framing (single-round targeted search).

> **Framing note — who the "user" is.** LineLens is not sold to plant operators; it is *watched* by recruiters and plant managers during a 60-second demo. So "table stakes" here does **not** mean "everything a real OEE product needs" — it means **"what a factory-literate viewer must see (and see done correctly) before they trust the demo."** A missing operator-login screen costs nothing here; a Performance figure above 100% or a small-stop miscategorised as downtime is fatal. This reframe is the load-bearing idea of the whole document, and it converts several real-product table stakes into MVP anti-features (see §Anti-Features).

## Feature Landscape

### Table Stakes (Factory-Literate Viewers Expect These)

Missing or wrong = the viewer silently concludes "the author doesn't actually know manufacturing" and dismisses the demo. These are the credibility floor. All are already in PROJECT.md Active requirements unless marked (gap-fill).

| Feature | Why Expected (credibility trigger) | Complexity | Notes |
|---------|-----------------------------------|------------|-------|
| **OEE waterfall A×P×Q per line/shift** | The canonical OEE visual; ISO 22400 *and* oee.com/Vorne both define OEE = A×P×Q. A dashboard that shows a bare % without the three-factor decomposition reads as a toy. | MEDIUM | Waterfall (100% → −Availability → −Performance → −Quality → OEE). Verified formula in domain research §2. |
| **Performance ≤ 100% validation guard** | A factory person's fastest "this is fake" tell is P > 100% (means Ideal Cycle Time is mis-set). Showing the guard *demonstrates* domain literacy. | LOW | Flag/clamp + visible warning when P > 100%. Verified mandatory rule, §2. |
| **Correct loss classification** | Small stops → **Performance** (not downtime); changeover → **Availability** (Setup & Adjustments). Getting this backwards is the single most common amateur error. | MEDIUM | State machine must emit the right category. Verified §3. Configurable "changeover-as-planned" policy + planned→unplanned transition on overage (§2). |
| **Six Big Losses Pareto / Top Losses, stackable per shift** | The universal loss-analysis view across every commercial + OSS tool (Vorne, Evocon, Libre). Its absence signals "no real loss model underneath." | MEDIUM | Pareto by reason, grouped under the six categories; shift stacking. Verified baseline UX §4. |
| **Color-coded production timeline per line** | Standard "what happened when" strip (running/down/changeover/break). Expected on every operator/supervisor screen. | MEDIUM | Segmented time strip per line; color = state. Verified baseline UX §4. |
| **Andon board — all lines, one screen** | The floor scoreboard. **Minimum content per line = production state (Running/Down/Changeover/Break) + good count + target count**, updating live. Anything less isn't an andon. | MEDIUM | SSE push (per stack constraint). Verified minimum set §4. This is the "at-a-glance plant health" screen. |
| **Shift + planned-production-time handling** *(gap-fill)* | Availability = Run Time / **Planned Production Time**, and PPT excludes breaks/lunch and no-intent time (Schedule Loss). Wrong shift/break handling = wrong Availability = a factory person spots it instantly. | MEDIUM | Time-window config defining shift/day boundaries; breaks excluded from PPT; OEE aggregated **per shift at minimum**. Ties to open question: Indonesian 2-vs-3-shift patterns (PROJECT.md §Open research). |
| **Reason codes organised as a grouped tree** *(gap-fill)* | Real tools present reasons as a short, grouped tree (operator language), each mapping up to a Six-Big-Losses category. A flat/random reason list makes the Pareto look synthetic. | LOW | Data model + seed taxonomy only. Reasons are **generated by the simulator** (modeling operator input) — no live entry UI needed (see anti-features). Verified: reason data is operator-sourced, not sensor-sourced (§4). |
| **Calibrated, realistic OEE distribution** | A too-perfect plant reads as fake. Verified reality: peak 55–60%, more lines <45% than >85%. | LOW (config) | Most lines 50–65%, one showcase ~85%, one problem line <45%. Verified against Evocon 3,500-machine dataset (§2). Already a PROJECT.md requirement. |
| **On-screen shift summary (the "report" a viewer expects)** *(gap-fill)* | Plant managers expect a shift/daily summary bundling OEE-by-line + downtime Pareto + top losses for handoff. **This need is already satisfied by the DDS screen + per-shift Pareto** — call it out so it isn't rebuilt separately. | LOW (reuse) | No separate report engine for v1. Downloadable PDF/CSV is deferred (see MVP §Add-after-validation); scheduled/emailed reports are an anti-feature. |

**Infrastructure table stakes** (viewers don't see these directly, but they make the above real — belong in ARCHITECTURE.md, listed here for completeness): MQTT (Mosquitto) telemetry stream, ingestion worker → Postgres state intervals, SSE real-time transport. Without them the "real-time" claim is theatre.

### Differentiators (The Reason This Portfolio Piece Exists)

Not expected — these are where LineLens wins the 60-second demo. Each aligns with PROJECT.md Core Value ("machine downtime = broken customer promises").

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **OEE → DIFOT drill-down (the money shot)** | Every OEE tool stops at the machine; LineLens continues to the *customer order*. "Breakdown on Line 2 → 3 orders late this week," shown as a live drill from a late/at-risk order down to the contributing machine loss event. This is the single scene the demo is built around. | HIGH | Simulated order book (demand per SKU/day) linked to production output → DIFOT % (in-full, on-time), then order → contributing line/machine loss events. Verified: no OEE-segment precedent found (§5). **Framing guardrail: "bridge," never "nobody has done this"** — Celonis does order-delay from ERP process data. |
| **"Inject breakdown" demo control** | Turns a static dashboard into a *live proof*. One button/HTTP call visibly cascades OEE ↓ → andon turns red → DIFOT at-risk → drill-down explains it. This is what makes the GIF compelling and what a viewer remembers. | MEDIUM | HTTP endpoint + dashboard button. Requires the full pipeline to already be live so the cascade is real, not scripted. The demo's dramatic beat. |
| **One-command living virtual plant (built-in simulator)** | `docker compose up` → a self-running factory streaming believable events, no data setup, no external feeds. Removes the "empty dashboard / needs real data" problem that kills most portfolio analytics demos. This *is* the demo-mode feature for a portfolio audience. | HIGH | Per-machine state machine mapped to Six Big Losses; Sparkplug-B-style topics + PackTags-lite JSON. The credibility of every table-stakes feature above rides on this producing realistic data. |
| **Daily Direction Setting (DDS) screen** | Shows LineLens speaks the *management* language, not just the sensor language — the artifact a plant/production manager runs their morning meeting from. Differentiator vs pure-telemetry tools. | MEDIUM | (a) Yesterday: safety/quality/delivery + OEE + top loss; (b) top-3 actions today with owners; (c) escalation status. Verified spec §6 (single-source Augmentir — keep generic, **no IWS/P&G tiering claims**). Doubles as the "shift report" table stake. |

### Anti-Features (Deliberately NOT Built)

Two classes: (1) explicit PROJECT.md Out-of-Scope items, and (2) real-OEE-product table stakes that the portfolio reframe demotes to anti-features. Documenting both prevents scope creep from either "make it a real product" or "add the industry-standard feature" pressure.

| Feature | Why It Seems Required | Why It's Wrong Here | Do Instead |
|---------|----------------------|---------------------|------------|
| **Interactive operator reason-code entry UI** (tablet form, sub-15s selection, reason-tree editor) | It's a genuine table stake in *real* OEE products, and the search surface is full of "under 15 seconds" UX advice. | No operators watch this demo. A data-entry workflow adds surface area and demo dead-air with zero viewer payoff. | Simulator **auto-generates** reason codes (models operator input). Reason *taxonomy* exists as a table stake; the *entry UI* does not. Optional: a single non-interactive "reason annotated" tooltip on the timeline. |
| **Configurable / custom dashboard builder** (drag-drop pre-built widgets) | Listed as baseline UX #6 in the domain research; every commercial tool has it. | Config surface with no demo value — a recruiter never builds a dashboard in 60 seconds. Pure time sink. | Ship **fixed, curated, opinionated views**. The narrative is the product, not the flexibility. |
| **Downloadable PDF/CSV report export + scheduling/emailing** | Real shift-handoff workflows lean on exported reports. | Report scheduling/emailing is infra (SMTP, cron, templating) invisible in the demo. CSV export is a 5-minute afterthought at best. | On-screen DDS + per-shift Pareto covers the "report" need for v1. Static PDF/CSV export deferred to v1.x (§MVP). Scheduling/emailing: never for a demo appliance. |
| **Waste / scrap-yield-in-currency module** | Rupiah/dollar figures make impact visceral. | Out of Scope (PROJECT.md). Pareto of losses already tells the money story; DIFOT tells the *customer* story more powerfully than currency. | Loss Pareto + DIFOT order impact. Revisit only if a viewer asks "what does it cost." |
| **Predictive maintenance / Markov machine-state model** | "AI/predictive" is a recruiter magnet. | Out of Scope (v2). Cross-links future MarkovLens; building now dilutes the one clear story. | Narrative hook only ("v2 will predict this"). Keep the seam clean for later cross-link. |
| **Real machine / PLC / sensor ingestion** | "Connects to real machines" sounds impressive. | Out of Scope + directly contradicts the honesty guardrail (this is an *honest simulated build*). Claiming or half-building real connectivity is a credibility landmine. | Keep it explicitly synthetic/clean-room. Sparkplug-B-style topics make the *path to* real ingestion obvious without pretending to have it. |
| **Full Sparkplug B compliance** (protobuf, birth/death lifecycle) | Standards-completeness looks rigorous. | Out of Scope. Adds protocol plumbing with zero demo-visible value; topic convention + JSON already reads as credible. | Topic namespace convention + PackTags-lite JSON (Status+Admin subset). Verified sufficient (§7). |
| **Full PackML 17-state machine** | Standards-completeness again. | Out of Scope. 17 states is simulator complexity no viewer perceives. | Minimal verified subset from ISA-TR88.00.02-2015 (verify state list before coding — open question). |
| **Multi-tenant / auth / user management / RBAC** | Every "real" app has login. | Out of Scope — this is a demo appliance, not SaaS. A login wall is friction between the viewer and the money shot. | No auth. `docker compose up` → straight to the dashboard. |
| **DuckDB analytical layer** | Sibling StockLens uses DuckDB; consistency is tempting. | Out of Scope up front. Real-time floor events ≠ batch analytics; Postgres aggregates are the right tool. | Postgres aggregates. Add DuckDB *only* if they prove insufficient (they won't at this scale). |
| **Live hosted demo URL** | A clickable link beats a GIF. | Out of Scope for v1 (stretch). Hosting a stateful MQTT+worker+DB stack on hobby tier is fragile — a dead link is worse than no link. | **GIF + `docker compose up` is the mandatory demo path.** Live URL only as a stretch on free tier. |
| **TPM / IWS tiered-meeting structure as a feature** | Naming IWS/P&G tiering sounds authoritative. | Not documented in verified sources — claiming it is a fabrication risk (honesty guardrail). | DDS screen + narrative only. Generic "daily direction setting," no proprietary-methodology claims. |
| **Months of historical data / long-range trend store** | Real dashboards show 7–14 day trends and history. | The plant is born at `up`; there is no history, and faking months of it is wasted effort a viewer won't scroll. | Live + current-shift + yesterday (enough for DDS comparison). A short in-memory/seeded "yesterday" is sufficient. |

## Feature Dependencies

```
Simulator (state machine → MQTT telemetry)
    └──requires──> Shift calendar / Planned Production Time model
                       (Availability is undefined without PPT)

Ingestion worker (MQTT → Postgres state intervals + loss categories)
    └──requires──> Simulator
    └──requires──> Reason-code taxonomy (grouped tree)

OEE Engine (A×P×Q, P≤100% guard)
    └──requires──> Ingestion worker
    └──requires──> Shift calendar (per-shift aggregation)

OEE Waterfall ────requires──> OEE Engine
Six Big Losses Pareto ──requires──> Ingestion worker + Reason-code taxonomy
Production timeline ──requires──> Ingestion worker (state intervals)
Andon board ────requires──> Simulator (live state) + SSE transport

DIFOT module ──requires──> OEE Engine (good-count output) + Simulated order book
    └── Drill-down ──requires──> DIFOT + persisted loss events (order → loss-event link)

DDS screen ──requires──> OEE Engine + Pareto (top loss) + DIFOT (delivery)
    (synthesis screen — depends on nearly everything; build last)

Inject-breakdown control ──requires──> full live pipeline (Simulator→OEE→Andon→DIFOT)
    (the cascade must be real, so this lands after the pipeline is end-to-end)
```

### Dependency Notes

- **Everything requires the simulator producing correct data.** The table-stakes visuals inherit their credibility from the simulator's state machine and calibrated distribution — a beautiful waterfall over garbage events fails the factory-literate test. Simulator quality is the highest-leverage work item.
- **Shift calendar is an early, invisible dependency.** It underpins Availability. It's tempting to defer as "just a UI selector," but it changes the math — schedule it with the OEE engine, not the dashboard.
- **DDS and Inject-breakdown are the last two features**, because both are compositions of everything else. Inject-breakdown especially needs the whole cascade live to be honest rather than a canned animation.
- **DIFOT drill-down requires loss events to be persisted and linkable to orders**, not just aggregated. Design the ingestion schema so individual loss events retain machine/line/timestamp identity from the start, or the money-shot join becomes a painful retrofit.

## MVP Definition

The MVP is the full PROJECT.md Active list — scope is already disciplined. Prioritisation below is *within* that set (build order), plus what explicitly waits.

### Launch With (v1) — the demo cannot land without these

- [ ] **Simulator + shift calendar + calibrated distribution** — the living plant; source of all credibility.
- [ ] **Ingestion → OEE engine (A×P×Q, P≤100% guard, correct loss classification)** — the correctness spine a factory viewer scrutinises.
- [ ] **OEE waterfall + Six Big Losses Pareto + production timeline + andon board** — the four baseline UX patterns; their absence reads as "not a real OEE tool."
- [ ] **DIFOT module + order→loss-event drill-down** — the differentiator; without it this is just another OEE clone.
- [ ] **Inject-breakdown control** — the demo's dramatic beat and the star of the GIF.
- [ ] **DDS screen** — management-language proof + doubles as the shift report.
- [ ] **Distribution: public repo, MIT, README + hero GIF, one-command quick start, case study, ≥1 LinkedIn post + ≥1 application** — distribution is Definition-of-Done, not optional (PROJECT.md).

### Add After Validation (v1.x) — cheap wins, only if the core demo proves compelling

- [ ] **Static PDF/CSV shift-summary export** — trigger: a viewer/recruiter explicitly asks "can I take a report away?" Low effort once DDS data exists.
- [ ] **Configurable changeover-as-planned toggle surfaced in UI** — the *policy* is already built; exposing it as a visible setting is a small credibility flourish if demo feedback wants it.
- [ ] **Second/third shift-pattern presets** (Indonesian 2-vs-3-shift) — trigger: localising the story for a specific East-Java employer conversation.

### Future Consideration (v2+) — deliberately deferred (mostly PROJECT.md Out of Scope)

- [ ] **Waste/scrap-in-currency module** — defer: Pareto + DIFOT already carry the impact story.
- [ ] **Predictive maintenance (MarkovLens cross-link)** — defer: v2; keep the narrative seam clean.
- [ ] **Real PLC/sensor ingestion** — defer: only if market signal justifies; would change the honesty framing.
- [ ] **Live hosted demo URL** — defer: stretch; GIF + compose is the mandatory path.

## Competitor Feature Analysis

How the market handles each pattern, and LineLens's deliberate stance. (Vorne = market-leading edge appliance; Evocon = cloud SaaS w/ large benchmark dataset; Libre = Apache-2.0 OSS precedent, dormant since Mar 2022.)

| Feature | Vorne XL | Evocon | Libre (OSS) | LineLens approach |
|---------|----------|--------|-------------|-------------------|
| OEE A×P×Q + P≤100% guard | Yes, 140+ metrics | Yes | Yes (Grafana calc) | Yes — subset done correctly; guard shown as a *feature*, not hidden |
| Six Big Losses Pareto | Yes | Yes | Yes (Pareto + sunburst) | Yes — stackable per shift |
| Andon / floor scoreboard | Yes (real-time) | Yes | Yes (Grafana) | Yes — state+good+target minimum, SSE |
| Reason-code capture | **Operator input** (1–2 sensors for counts only) | Operator input | Operator input | **Simulator-generated** (models operator input) — no live entry UI |
| Custom dashboard builder | Yes (64+ reports) | Yes | Yes (Grafana) | **No** — fixed curated views (anti-feature) |
| Order/DIFOT linkage | Narrative throughput only | Narrative only | No | **Yes — causal drill-down (the differentiator)** |
| DDS / management view | Reports, not a DDS ritual screen | KPI dashboards | No | **Yes — dedicated DDS screen** |
| Data source | Real edge sensors | Real machine data | Real (InfluxDB) | **100% synthetic, honestly framed** |
| Deployment | Hardware appliance | Cloud SaaS | Self-host stack | **`docker compose up` demo appliance** |

Positioning takeaway: LineLens intentionally *narrows* on the two things the segment doesn't do (causal order-linkage + a management DDS screen) while matching the baseline four visuals, and *drops* the two things a portfolio demo doesn't need (operator entry UI, dashboard builder). It competes on narrative depth, not feature breadth.
