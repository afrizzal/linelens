# REQUIREMENTS — LineLens v1

Requirement quality bar: specific, testable, viewer-centric (the "user" of this product is a factory-literate demo viewer), atomic.

## v1 Requirements

### Simulator (SIM)

- [ ] **SIM-01**: Simulator runs a per-machine state machine (verified PackML-inspired subset) whose states map to the Six Big Losses; configurable plant layout (lines, machines, shifts, products with ideal cycle time)
- [x] **SIM-02**: Simulator publishes telemetry to Mosquitto using Sparkplug-B-style topics (`spBv1.0/LineLens/<type>/<line>/<machine>`) with PackTags-lite JSON payloads (Status + Admin subset: state, counts, cycle time, alarms)
- [x] **SIM-03**: Simulator stamps all events with accelerated sim-time at the source (event-time contract); no downstream component derives time from wall-clock
- [ ] **SIM-04**: Loss events carry operator-style reason codes auto-generated by the simulator (grouped taxonomy per Six Big Losses)
- [ ] **SIM-05**: A viewer can trigger "Inject breakdown" on a chosen line (HTTP control + dashboard button) and watch the cascade live
- [ ] **SIM-06**: Fleet realism is calibrated: most lines 50–65% OEE, one showcase line ~85%, one problem line <45%, with natural jitter (no too-perfect data)
- [x] **SIM-07**: Shift calendar model (shifts, breaks) defines Planned Production Time; breaks/no-production windows are excluded from PPT (Schedule Loss), changeovers are not

### OEE Engine (ENG)

- [ ] **ENG-01**: A single ingestion worker is the sole MQTT consumer and sole Postgres writer; raw machine events are persisted losslessly
- [ ] **ENG-02**: Worker derives state intervals from events and records every loss in one `loss_event` ledger (lost-time units, tagged to one of the Six Big Losses, retaining line/machine/time identity)
- [ ] **ENG-03**: OEE is computed with the preferred calculation (A = Run Time/PPT; P = Ideal Cycle Time × Total Count/Run Time; Q = Good/Total) aggregated per line and shift
- [ ] **ENG-04**: Loss classification is correct per verified definitions: small stops → Performance loss; changeover → Availability loss under a configurable "changeover as planned" policy, with planned→unplanned transition on target overage
- [ ] **ENG-05**: Built-in validation guards: Performance > 100% is flagged as misconfigured Ideal Cycle Time; no-runtime windows show "N/A" (never 0% or NaN); Total = Good + Reject invariant holds
- [ ] **ENG-06**: Live OEE handles in-progress intervals correctly (open-interval clamping) and produces identical results at different clock accelerations (2× vs 10× test)

### Dashboard (DASH)

- [ ] **DASH-01**: A viewer sees a real-time OEE waterfall (A×P×Q) per line/shift
- [ ] **DASH-02**: A viewer sees a Six Big Losses Pareto / Top Losses report, stackable per shift
- [ ] **DASH-03**: A viewer sees a color-coded production timeline per line (state bands over time)
- [ ] **DASH-04**: A viewer sees an andon board with all lines on one screen — production state (Running/Down/Changeover/Break) + good count + target count — updating live via SSE

### DIFOT Module (DIFOT)

- [ ] **DIFOT-01**: Simulated order book (demand per SKU/day) is fulfilled from simulated production output, producing a DIFOT % (in-full, on-time) view
- [ ] **DIFOT-02**: A viewer can drill down from a late/at-risk order to the contributing machine-level loss events (the money shot: "breakdown Line 2 → 3 orders late")

### DDS Screen (DDS)

- [ ] **DDS-01**: A viewer sees a Daily Direction Setting screen: yesterday's performance summary (safety/quality/delivery + OEE + top loss), top-3 actions today with owners, escalation status

### Distribution (DIST)

- [ ] **DIST-01**: Public GitHub repo (github.com/afrizzal), MIT license, English README with hero GIF and one-command quick start; `docker compose up` works from a clean clone (clean-machine smoke test)
- [ ] **DIST-02**: 60-second demo GIF captures the inject-breakdown → OEE → andon → DIFOT drill-down flow (deterministic/seeded demo path)
- [ ] **DIST-03**: Portfolio case study page published with honest framing ("simulated build informed by manufacturing experience at Integra + PLC background"; DIFOT positioned as bridge, no absolute-uniqueness claim)
- [ ] **DIST-04**: At least 1 LinkedIn process post published and LineLens attached to at least 1 real job application

## v2 Requirements (deferred)

- **Waste module** — scrap & yield in currency terms (first-cut candidate per original scope decision)
- **Predictive maintenance** — Markov machine-state degradation model (cross-link MarkovLens engine)
- **Real machine ingestion** — PLC/sensor connectivity; only if market signal justifies it
- **Live demo URL** — Railway/Fly.io hobby tier (stretch in distribution phase if time allows)
- **PDF/CSV shift report export** — on-screen DDS covers v1

## Out of Scope

- **Multi-tenant / auth / user management** — demo appliance, not SaaS
- **Full Sparkplug B compliance (protobuf, birth/death lifecycle)** — topic convention + JSON is sufficient; no demo value
- **Full 17-state PackML machine** — simplified verified subset only
- **DuckDB analytical layer** — Postgres SQL views suffice at demo data volume
- **Operator reason-code entry UI** — simulator auto-annotates; the viewer is not an operator
- **Custom dashboard builder / report scheduling / emailing** — real-product features with zero demo value
- **TimescaleDB / table partitioning** — over-engineering below ~100GB; retention cap instead
- **TPM/IWS-specific tiering claims** — DDS screen only; tiering structures not documented in verified sources
